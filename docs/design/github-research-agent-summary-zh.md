## 〇、战略背景

Hummingbird 的愿景是一个**技能社区**——开发者在这里展示自己的真实技术能力、互相发现、交流和协作。GitHub 调研 Agent 是这个社区的**第一个切入工具**：

- **为什么从 GitHub 开始**：开发者群体是平台的初始用户，GitHub 是最直接可量化的技能数据源
- **为什么不是招聘工具**：社区先行，让用户有动力主动完善自己的技能画像；招聘场景是当社区数据积累到一定规模后**自然涌现**的价值，不是起步目标
- **长期图景**：GitHub 只是第一个数据维度，未来可扩展到其他技能证据（StackOverflow、个人博客、项目协作记录等），最终形成一个立体的、可验证的开发者技能图谱

---

## 一、这个功能是什么

给定一个 GitHub 用户名，AI Agent 自动去"翻"这个人的 GitHub 主页、代码仓库、贡献记录，最终生成一份**结构化的开发者技能档案**——帮助社区成员更好地了解彼此的技术背景，促进发现和协作。

产出示例（简化）：

> **张三** — 全栈工程师，活跃 6 年，擅长 TypeScript/Python，深耕 Web 后端和 DevOps 领域。
> 维护了 2 个千星开源项目，向 React、Next.js 等知名项目提交过 PR。
> 近两年活跃度稳定，代码审查参与度高，具备团队协作型贡献者特征。

所有结论都附带**可追溯的证据链接**（具体仓库、PR、Issue），不是空口白话。

---

## 二、解决什么问题

| 现状痛点 | Agent 解决方式 |
|---------|-------------|
| 开发者缺少展示真实技能的渠道 | 从 GitHub 公开数据自动生成**可验证的**技能画像 |
| 手动整理 GitHub 履历耗时 | 一个人的分析 < 3 分钟自动完成 |
| 看不出"深度" | AI 区分"写过 Python 脚本" vs "维护 Python 框架"，给出分级评估 |
| 社区成员之间难以互相发现 | 标准化的技能档案让"找到对的人"变得容易 |
| 跨仓库贡献难发现 | 自动搜索该用户在所有公开项目中的 PR、Issue、Code Review |

---

## 三、产出档案包含哪些维度

| 维度 | 内容 |
|-----|------|
| 基本信息 | 姓名、头像、公司、地域、社交账号、GitHub 年龄 |
| 技术技能 | 编程语言（按代码量排序 + 熟练度分级）、框架工具、技术领域 |
| 经验与职业阶段 | 活跃年数、贡献趋势（上升/稳定/下降）、工作模式（职业型/爱好者型） |
| 开源影响力 | 代表作品（星数、Fork数）、对外部项目的贡献、社区参与度 |
| AI 综合评价 | 一句话概括、核心优势、擅长方向、数据质量备注 |

熟练度分4级：入门 → 熟悉 → 熟练 → 专家
领域深度分5级：接触 → 了解 → 深入 → 专家 → 顶级

## 四、技术方案概览（非技术人员版）

```
用户在网页输入 GitHub 用户名
        ↓
后端启动 AI Agent（运行在 Vercel 云端）
        ↓
Agent 自动调用 GitHub API 收集数据（3-5 轮）
        ↓
Agent 调用 Google Gemini AI 分析和总结
        ↓
生成结构化档案，存入数据库
        ↓
用户在网页实时看到进度和结果
```

- **不需要额外服务器**：Agent 跑在现有 Vercel 部署上（Vercel Workflow 机制）
- **不需要目标用户授权**：只分析 GitHub 上的公开数据
- **不修改现有功能**：作为侧边栏的新页面独立存在

## 五、成本分析

### 开发成本

预估 **9-13 个工作日**，可分 5 个阶段交付：

| 阶段 | 内容 | 预估 |
|------|------|------|
| 环境搭建 | 安装依赖、配置 Workflow、跑通最小 demo | 1-2 天 |
| 数据采集 | 实现 GitHub 数据收集（复用现有代码） | 2-3 天 |
| AI 分析 | 设计提示词、调优输出质量 | 2-3 天 |
| 前后端对接 | API、数据库、前端页面 | 2-3 天 |
| 上线打磨 | 错误处理、测试、部署 | 1-2 天 |

### 运行成本

| 阶段 | AI 费用 | 平台费用 | 调研量 | 瓶颈 |
|------|--------|---------|-------|------|
| 开发/原型期 | **$0**（Gemini 免费额度） | **$0**（Vercel 免费额度） | ~25 次/天，~750 次/月 | Gemini 免费额度（250 请求/天） |
| 早期用户 | ~**$10/月** | $0-20/月 | ~1,000 次/月 | 无技术瓶颈，取决于实际用户量 |
| 规模化 | ~**$50/月** | ~$20/月 | ~5,000 次/月 | 同上 |

**单次调研成本 ≈ $0.01**（约 7 分钱人民币），主要是 AI 模型调用费。GitHub API 免费。进入付费后 Gemini 的请求限额大幅放宽（Tier 1: 2000 次/分钟），瓶颈不再是技术限制而是实际业务量。

### 免费额度详情

| 资源 | 免费额度 | 每次调研消耗 | 支撑量 |
|------|---------|------------|-------|
| Google Gemini API | 250 次请求/天 | 5-10 次请求 | ~25-50 次/天 |
| Vercel Workflow 事件 | 50,000 个/月 | ~50 个 | ~1,000 次/月 |
| Vercel 函数调用 | 100,000 次/月 | ~15 次 | ~6,000 次/月 |
| GitHub API | 5,000 次/小时 | ~50-100 次 | 基本无限 |

**结论**：原型阶段完全免费，日均 25 次调研足够验证产品价值。

## 六、竞品与生态位

### 市面上有什么

| 产品/工具 | 做什么 | 不足 |
|----------|-------|------|
| GitHub Profile README Stats | 生成贡献统计图片 | 纯数字，无分析，无技能推断 |
| OctoProfile / Profile Summary | 可视化 GitHub 数据 | 只有图表，没有 AI 分析和能力洞察 |
| LinkedIn | 职业社交平台 | 自述为主，难验证，技术深度缺失 |
| 各类 developer portfolio 工具 | 聚合展示开发者作品 | 需要手动维护，无自动分析 |

### 我们的差异化

1. **AI 驱动的技能推断**：不只是统计"用了什么语言"，而是推断"用到什么程度"
2. **跨项目贡献分析**：自动发现开发者对其他开源项目的贡献（手动整理很难做到）
3. **社区化的技能展示**：档案融入 Hummingbird 社区，促进成员之间的发现和连接
4. **平台内数据闭环**：与用户档案、项目目录等现有功能打通，随着社区成长持续增值

### 局限性（需告知用户）

- 只分析 GitHub 公开数据，不包含私有仓库
- AI 推断的技能评级是参考性的，不是认证
- 非 GitHub 活跃的开发者（如主要用 GitLab、Bitbucket）信息会不完整
- 部分开发者的主要贡献通过邮件补丁（如 Linux 内核），GitHub 上不可见

## 七、风险与注意事项

| 风险 | 影响 | 应对 |
|------|------|------|
| Gemini 免费额度缩减 | 开发期调研量受限 | 可切换 AI 模型（架构已预留切换能力） |
| GitHub API 变更 | 数据采集中断 | 使用官方 API，非爬虫，风险较低 |
| AI 输出质量不稳定 | 技能评级偏差 | 标注"AI 推断"，附证据链接，人工可复核 |
| 隐私合规 | 用户投诉 | 仅用公开数据，提供删除机制，定位为技能展示而非背调 |
| Vercel Workflow 是较新产品 | 可能有 bug 或 API 变化 | 步骤拆分清晰，每步可独立重试 |

## 八、决策点

以下问题需要确认后才能进入实施：

1. **优先级**：此功能排在当前 roadmap 的什么位置？是否排在项目目录（HB-17）之后？

2. **MVP 范围**：
   - 是否第一版就需要前端 UI？还是先做后端 Agent + API，前端后补？
   - 是否需要支持批量调研（导入用户名列表）？建议 v1 不做。

3. **触发方式**：
   - 用户手动输入用户名触发？
   - 用户连接 GitHub 后自动触发？
   - 还是两者都要？建议 v1 只做手动触发。

4. **AI 模型选择**：
   - 确认使用 Google Gemini（免费额度最多）？
   - 还是考虑其他（如 Claude API，质量更好但无免费额度）？

5. **数据展示**：
   - 调研结果是否公开给所有用户，还是仅发起人可见？
   - 被调研的 GitHub 用户如果也是 Hummingbird 用户，是否通知他？

6. **是否交给 Agent 实施**：
   - 技术文档已足够详细，可以直接交给 coding agent 执行。
   - 建议按 5 个阶段分批交付，每阶段验收后再进行下一步。
